# v0.2 账号、材料导入与模拟计费

日期：2026-11-05。v0.1 经用户验收且 PR #2 的 Docker/单测/接口/浏览器 CI 绿色后合并 main；后续在 feature/careerlens-accounts-import 开发，不能沿用 v0.1 的人工批准合并新功能。

## 边界与数据

- Vue 用户工作台、账号与管理员视图共用原有设计 token，通过 BFF 调 Java。JWT 使用成熟 JOSE 库 HS256，密码 BCrypt，仅保存 hash；浏览器 token 只放 sessionStorage。
- Java 使用 H2/JDBC 与 Docker 数据卷保存用户、额度、分析消费、模拟充值和设置，不保存简历/JD 正文。启动凭据和 JWT 签名密钥来自运行时环境。
- 新用户默认 10 次额度，一次成功分析扣 1 次，失败退款；并发扣费使用数据库原子更新。单实例启动恢复中断的预扣。客户端不自动重试分析，避免重复消费。
- 充值金额使用整数分，1 元 = 10 次额度；订单创建与模拟确认均幂等，禁止用户操作别人的订单。只有 SIMULATED_PAID 状态可发额度，不涉及支付网关、真实收款或退款。
- 管理员可查看用户、余额、消费与充值，调整额度和平台分成比例。分成以 basis points 保存（0–10000），按订单创建时比例快照记账，不影响用户购买额度；不执行真实结算。
- MD/TXT/PDF/DOCX 每文件最多 2 MiB，PDF 最多 30 页。文件只经过请求内存，解析后回填可编辑文本，不保存原文件；扫描 PDF/加密 PDF 给出可操作错误。简历/JD 原有字符上限不变。
- Python 独占模型配置。经用户授权，从本机 Codex 配置读取当前中转和 key，生成被忽略的运行时环境配置，不输出 key、不提交配置。兼容 chat/responses 两种 HTTP 协议。

## API

所有业务响应继续为 `{code,msg,data}`；trace 走 header。分析、文件、账户和充值需要 Bearer JWT；管理员接口另检查 role=ADMIN。

- POST /api/v1/auth/register、/login，GET /api/v1/auth/me。
- GET /api/v1/account：余额、分析消费与最近充值。
- POST /api/v1/documents/text：multipart file + target=resume|jd，由 Java 调 Python 解析。
- POST /api/v1/recharges：amountCents、idempotencyKey；POST /api/v1/recharges/{id}/simulate-confirm。
- GET /api/v1/admin/overview、/users、/recharges、/settings；PUT /api/v1/admin/settings；POST /api/v1/admin/users/{id}/quota。

## 验收与回滚

验证身份伪造/过期、越权、重复注册、并发扣费、失败退款、重复支付、跨用户订单、比例上下限、文件类型/体积/解析失败；Docker 中执行单测，并跑真实请求与用户/管理员浏览器流程。原 v0.1 四镜像保留，回滚不删除数据卷。账号数据备份和真实支付另行接入，不把模拟订单当真实财务记录。
